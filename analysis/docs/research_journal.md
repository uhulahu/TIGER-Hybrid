**关于sinkhorn**:
- 看到rqkmeans与rqvae的差异，开始思考原因。由于用的rqvae是使用了sinkhorn来减少分配冲突的，而rqkmeans没有用，因此直接怀疑sinkhorn，对sinkhorn在rqvae中的运用进行反思，具体来说之前的实验中rqvae中两处使用的sinkhorn承担不同功能：
  - **训练时sinkhorn**：在第三层vq使用sinkhorn替代贪心式码字分配，这会反过来让rqvae的模型权重和码本做出适应性调整，会反过来“塑造”tokenizer，改变整个 RQ-VAE 的表示几何和层级信息分配。
  - **推理时 / SID 导出阶段的 post-hoc Sinkhorn**：推理时对碰撞桶内的item使用sinkhorn重新分配L3 token来缓解碰撞，不改变码本。但是这会造成L3原本的语义发生扭曲，可能把 item 分到训练时不自然的 code 上。
- 训练时在 L3 的 VQ 中使用 Sinkhorn，和 SID 提取后再对碰撞组做 Sinkhorn 重分配，本质上是两件不同的事，也会有不同的影响。训练时 Sinkhorn 是“改变分配，并让表示空间逐渐适应这种分配”；推理时 Sinkhorn 是“在表示空间固定后，强行换一个离散标签”。
- 然后我们去掉 post-hoc sinkhorn 并做了统计分析： 
  - `data/Beauty/Beauty_t5_rqvae_260709-sk[0-0-0.003].npy`在导出时使用了sinkhorn；`data/Beauty/Beauty_t5_rqvae_260709-sk[0-0-0.003]-inferExtraOnly.npy`是同一个rqvae但导出时没用sinkhorn仅使用extra token得到的SID。
  - `rqvae/ckpt/Beauty/Jul-09-2026_02-06-03/sid_evaluation.txt`和`rqvae/ckpt/Beauty/Jul-09-2026_02-06-03/sid_evaluation_extraOnly.txt`中分别是两者的统计评估。
  - `rqvae/ckpt/Beauty/Jul-09-2026_02-06-03/sid_compare.md`中是对比结论。
  - **核心结论**：post-hoc sinkhorn 只是把信息从 extra token 搬到了 L3，并没有减少 L2 之后的总预测不确定性。
  - 它让L3同时包含了两类信号混在一起：语义区分，唯一性驱动的身份区分。但生成模型无法知道二者的区别，它会把所有 L3 token 都当成同一种“细粒度语义标签”学习。
  - 相比之下，inferExtraOnly 职责分离更干净，明确承认前三层在量化意义上它们确实无法区分，因此加了最后一层桶内身份编号。
- 我们跑了下游实验，发现用去掉了post-hoc Sinkhorn 的`data/Beauty/Beauty_t5_rqvae_260709-sk[0-0-0.003]-inferExtraOnly.npy`作为SID真的比`data/Beauty/Beauty_t5_rqvae_260709-sk[0-0-0.003].npy`在下游生成模型上表现更好（测试集指标更高），日志在`model/logs/tiger_baseline_ce_inferExtraOnly.log`。


**关于 extra token**:
- 后来我们又觉得TIGER原文用的用来解决SID碰撞的extra token可能并不完美，因为它相当于纯随机/哈希的分配，是 SID 体系里最缺乏语义的一层，缺乏可供下游生成模型学习进一步区分能力的规律。当然，“随机分配”不等于“模型一定学不会”，真正决定它是否难学的是：在已经知道前三层 SID 的条件下，用户历史中是否还有足够的信息，能够区分碰撞桶里的具体 item。
- 难学的情况是：如果前三层前缀碰撞的两个item A、B 不仅内容极其相近，行为分布也很接近，那么即使给定用户历史，模型也无法稳定判断最终交互的是 A 还是 B。对于大小为 m 的碰撞桶，如果历史几乎不提供桶内区分信息，那么 suffix 最佳准确率可能只有 1/m。
- 所以 extra token 的核心问题是：它要求生成模型用用户行为预测一个量化空间本身无法解释的 item identity，且随机编号在不同桶之间没有可迁移规律。最终 token 只能依赖前缀做局部分类，几乎没有跨桶泛化能力。
- 然后我们通过`model/analyze_prefix_hit.py`中的脚本做了个实验试图验证：extra token 是否真的伤害了模型？具体来说，是在tiger_baseline_ce_rqkmeans上做了一个前三层正确率与完整 SID 正确率的分析，结果发现并非我们想象中那么夸张（具体数据在`model/analyze_prefix_hit.py`末尾注释中）：
  - $R_{prefix3}​@20$ - $R_{full}​@20$ = 0.0918 − 0.0875 = 0.0043，差距很小。也就是说，即使有一个完美方法，只要正确前三层出现，就一定能选中桶内正确 item，Recall@20 的上限也只是从 0.0875 提升到 0.0918。
  - 在所有 19,979 个 full-SID miss中，前三层已经正确、只错在 extra token：138，占 0.7%；前三层本身就错了：19,841，占 99.3%
  - ==> 即使完全消除 extra-token 问题，也只能修复极少数失败；真正的瓶颈是L1+L2+L3，是模型没有生成正确的语义前缀。

**改造 extra token**:
- 尽管我们已经证明瓶颈不在extra token，但是苍蝇肉也是肉，这可能成为我们这么多实验中唯一的正面改进。
- 简单地说，SID仍然是4-token，但是我们新增一个learned L4 codebook替代原extra token。这个L4在前三层码本训练完并冻结之后，用 Constrained K-means 对第三层之后之后的量化残差进行训练。分配码字时在每个L1L2L3前缀碰撞桶内使用匈牙利算法保证单射。使用加权量化损失，对碰撞的item的损失权重 ×$\lambda$，以防止损失信号少量的碰撞item防非碰撞item淹没。不过：最新的不加权版本`model/logs/tiger_kmeans_L4_lam1.log`已经跑出来了，强于$\lambda=10$的版本`model/logs/tiger_kmeans_L4_lam10.log`。

**关于SID统计分析**，我们写了一个脚本 `eval_sid.py` 来对tokonizer导出的SID进行统计评估，包括码各层码本利用率、前缀条件熵等等。我们用这个脚本评估了很多尝试，观察到的现象：
- 关于码本利用率：
  - 通常情况下，码本利用率随码本层级逐渐升高。这符合朴素的直觉：tokenizer本身用的就是残差量化(rqvae/rqkmeans)，深层码本拟合浅层码本的残差，自然浅层负责粗粒度路由，深层负责细粒度区分。
  - 原始rqvae训练的码本，L1利用率较低，L2、L3码本利用率较高，L3通常是100%。`data/Beauty/Beauty_t5_rqvae_260709-sk[0-0-0.003].npy`的三层码本利用率为：`21.3% -> 100% -> 100%`。
  - kmeans训练的码本，L1、L2、L3利用率：`100.0% -> 98.4% -> 100.0%`，轻微的沙漏型。
  - 加了LETTER协同正则化的rqvae导出的码本，利用率为沙漏型。L1超过80%，L2不到50%，L3 100%。
- 关于条件熵：
  - 从H(L1)到H(L2|L1)再到H(L3|L1,L2)的条件熵分布大多呈倒金字塔型，或者底部尖尖的梨形。H(L3|L1,L2)通常最低，没见过超过2的。`data/Beauty/Beauty_t5_rqvae_260709-sk[0-0-0.003].npy`的三个条件熵分别是：`5.5648 -> 6.4231 -> 1.5678`。
  - `data/Beauty/Beauty_kmeans_code.npy`的三个条件熵：`7.7262 -> 4.7436 -> 0.9314`。
- 能提高浅层码本利用率的，通常会让条件熵倒金字塔变得更扁平，H(L3|L1,L2)降低，信息前移。前两层训练中使用sinkhorn、CoST对比损失、rqkmeans都符合这个规律。
- 利用率和条件熵的形状是由各层码本所承担的功能和承担的量影响的。

关于瓶颈：
- `analysis/first_diff_distribution.ipynb`做了分析，发现L1的正确率只有5.66%，而正确率P(L2 correct∣L1 correct)=30.04%，P(L3 correct∣L1,L2 correct)=67.89%，P(L4 correct∣L1,L2,L3 correct)=95.74%。结论：SID 的预测难度极度前置，L1 是绝对准确率最低、且错误后不可恢复的主要路由关口；L4 几乎不是问题。
- 之前我们认为瓶颈在L1L2L3，不在L4 / extra token，现在我们更进一步，确定了，最大的瓶颈在L1。现在TIGER 的 recall 上限几乎完全由 L1 分类准确率决定，更准确的来说，正确 L1 能否进入 beam。


**TIGER训练过程观察到的现象**：
